# 地区の振り分け規則を D1 の JSON ドキュメントから読む

## 要約

1 本のフィードに複数の地区の記事が混ざる地域ニュースを地区ごとに振り分ける規則の置き場について、Cloudflare D1 に feed ごとの JSON ドキュメントとして置き、chatsumi が読み出してメモリに持つ形を選び、repo への直書き、運用の repo のファイル、Workers KV、docker01 に置く文書 DB を退けた。公開の repo に特定の地名を載せず、配備なしで規則を直せるようにするためで、Cloudflare の API への依存と、「保存を持たない」という原則を設定の読み出しに限って緩めることは受け入れる。

## 背景と課題

地域ニュースの RSS には、1 本のフィードに市内全域の記事が混ざるものがある。その新着を、地区ごとに分けて読みたい。

振り分けは、地名の別名の表との文字列一致で足りる。数万件の過去記事で試すと、分けたい地区が数個のとき、学習済みのモデルによる判定より別名の表のほうが正確で、CPU の乏しい置き場でも一瞬で終わった。表は、地区ごとの別名と、別名を含むが地区を指さない語（隣の市の駅名など）、地区ごとの通知先からなる。

この表には特定の地名が並ぶ。chatsumi は公開の repo なので、表をコードに書くと、利用者が見ている地域が誰にでも読める。また、表は記事を見ながら少しずつ育つので、直すたびにリリースと配備が要る形は重い。

## 判断の決め手

- 公開の repo に地名を置かない
- 配備なしで別名を足し引きできる
- chatsumi は状態を持たない窓口のままにする

## 検討した選択肢

1. chatsumi のコードに表を直書きする
2. 運用の repo（private）にファイルで置き、コンテナにマウントする
3. Workers KV に、feed ごとに JSON を 1 つ置く
4. D1 に、feed ごとに 1 行の JSON ドキュメントとして置く
5. docker01 に文書 DB（PocketBase など）を置く

## 決定

選択肢 4 を選ぶ。

- 表は `area_maps (feed_id TEXT PRIMARY KEY, doc TEXT CHECK (json_valid(doc)), updated_at TEXT)` に、feed ごとに 1 行で持つ。`doc` は別名・除外する語・どの別名にも当たらない記事の地区（既定の地区）・地区ごとの通知先を持つ JSON にする
- chatsumi は起動時と一定の間隔で全行を読み、Valibot で形を確かめてメモリに持つ。形が合わない行は捨てて、その feed は前に読めた版を使い続ける。起動してからまだ一度も読めていない feed の記事は、振り分けずに送らない
- chatsumi が持つのは読み取りだけの権限にする。表を書くのは chatsumi の外（`wrangler d1 execute` など）にする
- 通知先の webhook の URL は表に入れない。表には secret の名前だけを書き、URL は secret として chatsumi に渡す

### 結果

- 良い点: 公開の repo には、表の形と判定の処理だけが残る。テストは架空の地名で書ける
- 良い点: 別名の追加は、D1 への UPDATE 1 本で済む。SQLite の JSON 関数（`json_insert`、`json_each`）で、ドキュメントの一部だけを直せる
- 良い点: chatsumi は、読んだ表をメモリに持つだけで、保存も書き込みもしない
- 悪い点: chatsumi が Cloudflare の API に依存する。API の認証情報が 1 つ増える
- 悪い点: 表を編集する画面が無い。直すときは SQL を書く
- 悪い点: D1 の行には変更の履歴が残らない
- 悪い点: 「保存を持たない」という原則に、設定を外から読むという例外ができる

## 選択肢ごとの良い点と悪い点

- 直書き: いちばん単純だが、地名が公開される。直すたびにリリースが要る
- 運用の repo のファイル: 地名は公開されず、変更は PR で追える。ただし直すたびに配備が要る
- Workers KV: JSON を 1 つ置くだけで済むが、別名を 1 つ足すにも全体を読んで書き戻す
- 文書 DB: 管理画面が付くものもあるが、docker01 に配備とバックアップの対象が 1 つ増える
